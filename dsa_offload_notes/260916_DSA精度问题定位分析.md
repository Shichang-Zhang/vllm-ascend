## 0. 结论摘要（TL;DR）

**最重要的结构性事实（比任何单条猜测都重要）**：

> `fused_overlap` 路径下，**融合算子拿到的 host KV 就是"本进程的 host 视图张量"本身**。
> 即 `AscendSFAKVOffloadImpl._execute_fused_overlap_offload_decode` 调用
> `manager.get_fused_overlap_cpu_kv_inputs(layer_name)` → `get_local_host_kv_views(layer_name)`
> → `k_caches_cpu[layer_id] / v_caches_cpu[layer_id]`，然后 `_flatten_pa_cache(...)`（reshape，view 不是 copy）
> 直接作为 `full_kv_cache` / `full_k_rope` 传给算子。
> **Mooncake 下这个张量是 `torch.int8` 字节视图 `narrow()` 出来的类型化视图**（`mooncake_host_pool.py:211`），
> 与 MemFabric 下 `_restore_bfloat16_tensor` 造出的视图在**算子的角度看是同一种东西**。

**推论**：算子本身对后端无感知。凡"MemFabric 好、Mooncake 坏"的精度问题，**根因只能落在这 4 个后端相关差异点**：

| # | 差异点 | MemFabric（参照，正常） | Mooncake（异常） | 代码位置 |
| :--- | :--- | :--- | :--- | :--- |
| **D1** | host 池的分配与设备寻址 | `offload.empty(pin_memory=True)` 取自 MemFabric SHARED 池；非 0 rank 靠 rank0 指针广播 + GVA | `create_shared_segment(mmap=True, host_register=True)`；每 rank 自己的本地 NPU 视图 | `sparse_kv_offload_manager.py:611-659` / `mooncake_host_pool.py:75-147` |
| **D2** | membership plan 的发布 | planner 与算子**共用同一块内存**，`publish_plan()` 首行 `return`（零拷贝）；`owner_map` 与 `selection_membership_map` 是**同一个对象** | pinned 紧凑蓝图 → NPU staging → 段（两跳）；`owner_map` 与 `selection_membership_map` 是**两个不同对象** | `sparse_kv_offload_manager.py:790-882`、`1842-1882` |
| **D3** | current token KV 的写回 | `offload.sparse_copy(ptr 数组)`，**无需索引张量** | `index_select + index_copy_` + **C++ host callback 生成/刷新描述符** | `sparse_kv_offload_manager.py:1565-1648`；`csrc/torch_binding.cpp:2539-2712` |
| **D4** | P→D 的 prefill KV 落盘 | `SfaRemoteD2HConnector`（RD2H，MemFabric 自己的 RDMA 通路） | `MooncakeConnectorV1(dsa_pd_offload=true)`，Main 走 **D2RH** 写入 `location="npu:<dev>"` 注册的段 | `mooncake_connector.py:3357-3411, 790-932` |

**D2 里藏着一个此前未被指出的语义差异，是本文最推荐的优先验证项（见 §2.1）**：

```python
can_reuse_owner_plan = (skip_topk and owner_layer_id is not None
                        and layer_id > owner_layer_id
                        and self.fused_overlap_plan_topk == self.topk
                        and self.fused_overlap_plan_num_tokens == num_tokens
                        and owner_map is not None)
if can_reuse_owner_plan:
    if selection_membership_map.data_ptr() != owner_map.data_ptr():   # ← MemFabric 恒为 False；Mooncake 恒为 True
        plan_storage.copy_(owner_map[:num_tokens, plan_start:...], non_blocking=capturing)
    return True
```

MemFabric 下 `owner_map is selection_membership_map`，`data_ptr()` 相等 ⇒ **这行 copy 永远不执行**；
Mooncake 下两者不同 ⇒ **这行 copy 每次都执行**，把"上一层那份 plan 内容"搬到当前层的 map 里。
**也就是说：MemFabric 参照路径上这条跨层复用分支实际上是"空转"的，Mooncake 上才第一次真正生效。**
如果这份被复用的 plan 内容与当帧不匹配，就会读到错误的 top-k/槽位 ⇒ 症状正是"逻辑对了但停不下来"。

**优先级建议（结合你的补充信息）**：

| 优先级 | 方向 | 对应问题 | 本文小节 |
| :--- | :--- | :--- | :--- |
| **P0** | D2 的跨层复用内容陈旧（Mooncake 独有生效路径） | 问题 1（短输入+图模式复读），原理上也覆盖问题 2 | §2.1 |
| **P0** | D3 的描述符刷新时序 / 空批次 padding 的静默写 | 问题 1 | §2.2 |
| **P1** | D1 + Mooncake 存储侧：`index_copy_` 写 NPU 可寻址 host VA 的可见性 | 问题 1、2 | §2.3 |
| **P1** | 长输入特有：`max_num_topk_rows` 触顶 + host 池容量 + `num_blocks` 映射 | 问题 2 | §3 |
| **P2** | D4 / PR3：D2RH 落点、注册 location、失败块处理、多 writer 分区 | 问题 2（且可能是 Mooncake 存储而非 connector） | §4 |
| **P2** | 结构性不一致：同一 forward 内 `capturing` 与 `_in_graph_runtime()` 混用 | 问题 1 | §5.3 |

## 1. 前置：这轮排查的"参照实验"怎么用

你提供了一个很宝贵的对照条件：**fused+memfabric 精度正常，fused+mooncake 有问题**。
这把排查空间从"整个 DSA 链路"压缩到上面 **D1–D4** 四点。请按下面的方式把它用足：

```text
                     ┌──────────────────────────────────────────────┐
   参照组 A          │ fused_overlap=true + host_backend="memfabric" │  ← 精度正常（已知）
   （baseline）      │ + SfaRemoteD2HConnector                      │
                     └──────────────────────────────────────────────┘
                     ┌──────────────────────────────────────────────┐
   实验组 B          │ fused_overlap=true + host_backend="mooncake"  │  ← 精度异常（已知）
   （failing）       │ + MooncakeConnectorV1(dsa_pd_offload=true)    │
                     └──────────────────────────────────────────────┘
   A→B 之间只有 D1–D4 四点不同 ⇒ 根因必在其中
```

**关键提醒（避免误判）**：A 组与 B 组**换了两个东西**——host 后端（D1/D2/D3）**和** P→D 连接器（D4）。
如果只做 "A vs B" 对照，无法区分是 D1–D3（node 内）还是 D4（跨节点）。**建议用下面这个"混合组"把 D4 摘出去**：

| 组 | host_backend | 连接器 | 能区分什么 |
| :--- | :--- | :--- | :--- |
| A | memfabric | `SfaRemoteD2HConnector` | 参照（正常） |
| B | mooncake | `MooncakeConnectorV1(dsa_pd_offload=true)` | 全量 Mooncake（异常） |
| **C（建议新增）** | **mooncake** | **`SfaRemoteD2HConnector`** | ⚠️ 需确认能否跑：`sfa_pd_rd2h/worker.py` 目前**硬性要求 `transfer_backend="memfabric"`**（PR1 分析已核实），所以 C 组**当前可能起不来**。若能让它起来（例如把 target 注册成 MemFabric 能识别的地址），就能直接把 D4 摘掉 |
| **D（建议新增）** | memfabric | `MooncakeConnectorV1(dsa_pd_offload=true)` | 被 PR3 的连接器构造校验挡住（要求 `host_backend="mooncake"`），**不可用** |

**结论**：C/D 混合组在当前代码上大概率起不来 ⇒ **只能靠"单变量代码补丁 + 重跑 B"来二分**，见 §2/§3 每条假设附带的"建议改法"。

## 2. 问题 1（短输入 + 图模式 → 复读）的候选根因

### 2.1【P0】D2 的跨层 plan 复用：MemFabric 上恒为空转，Mooncake 上第一次真正执行

**代码事实（逐字核实）**

`pr16219: sparse_kv_offload_manager.py:1863-1882`：

```python
owner_layer_id = self.fused_overlap_plan_owner_layer_id
owner_map = self.fused_overlap_plan_membership_map
can_reuse_owner_plan = (
    skip_topk
    and owner_layer_id is not None
    and layer_id > owner_layer_id
    and self.fused_overlap_plan_topk == self.topk
    and self.fused_overlap_plan_num_tokens == num_tokens
    and owner_map is not None
)
if can_reuse_owner_plan:
    assert owner_map is not None
    if selection_membership_map.data_ptr() != owner_map.data_ptr():
        if capturing:
            torch_npu.npu.current_stream().wait_stream(self.fused_plan_stream)
        plan_storage.copy_(
            owner_map[:num_tokens, plan_start:FSA_SELECTION_MEMBERSHIP_REQUIRER_COLUMNS],
            non_blocking=capturing,
        )
    return True
```

**两个后端下 `owner_map` 分别是什么**

| 后端 | `fused_overlap_planner_membership_map` 指向谁 | `owner_map` 与 `selection_membership_map` 关系 | `data_ptr()` 相等？ | 那行 copy |
| :--- | :--- | :--- | :--- | :--- |
| MemFabric | `membership_map` 本身（`:878`） | **同一个张量** | ✅ 相等 | **永不执行（空转）** |
| Mooncake | `planner_map`（CPU pinned 紧凑蓝图，`:854`） | 两个不同对象 | ❌ 不等 | **每次都执行** |

（对应的分支代码：Mooncake 走 `_requires_fused_membership_staging()` 为真的那一支，`:815-854`；MemFabric 走 `else` 那一支，`:855-878`。）

**这条差异为什么能解释"复读"**

`skip_topk` 是**逐层**配置（`sfa_v1.py:458`：`self.skip_topk = kwargs.get("skip_topk", False)`；`:1460-1466` 用它决定是否复用 `topk_indices_buffer`）。
所以确实存在"**某几层 `skip_topk=False`（跑 planner）→ 后面某层 `skip_topk=True`（走复用）**"的层组合。

在这条路径上，Mooncake 会把 `owner_map` 的 `[0:num_tokens, plan_start:16392]` **整片**复制到当前层的 `plan_storage`。而：

1. **`can_reuse_owner_plan` 不校验"这份 plan 是否属于当帧的同一批 token"**，也不校验 `plan_storage` 里**超出 `num_tokens` 的行**（后半段是上一帧/上一个请求的残留）。算子按 `control[2]=topk`、`control[3]=plan_start` 读 plan，只要行号在 `num_tokens` 内就认为是有效计划。
2. **跨帧残留**：`fused_overlap_plan_owner_layer_id` / `fused_overlap_plan_num_tokens` / `fused_overlap_plan_membership_map` **从不按请求清除**（只在 `__init__` 置初值）。只要"上一次写入 owner 的那一帧"与"当帧"`num_tokens` 恰好相同（短输入 + 固定 batch 时极易相同），复用条件就成立。
3. **每一帧的 top-k 集合都不同**（decode 每步都变），plan 编码的是"第 pos 个 top-k 该用哪个 slot / 是否 miss"。

⇒ 一旦复用命中的是一份**属于别帧/别请求的 plan**，算子就会按错误计划去读 host KV 和 selection buffer，**当前 token 的 K/V 可能被放到错误的槽位、历史 token 从 host 读到别人的 KV**。这与"逻辑推理成功但输出无法停止（复读）"高度吻合。

**为什么"不开图模式就好"？**

`!capturing`（eager）分支里 `can_reuse_owner_plan` 同样会被求值，所以这条路径理论上 eager 也会走。**但 eager 与 graph 的关键区别在于**：

- eager 下 planner 与 copy 都是**同步**（`run_planner(enqueue=False)` + `publish_plan(non_blocking=False)`，`:1947-1979`），且 `offload_new_kv` 的写回走 current stream（`use_side_stream` 为 False，`:1388-1394`），整条链是**逐步串行、每步都真正跑完 planner**；
- graph 下 plan 的产出由 host callback 驱动、写回在 `current_kv_save_stream` 上异步，**跨帧残余的可见性更高**（上一帧的 `owner_map` 内容与当帧的 `plan_storage` 在时间上重叠）。

⚠️ **这是一个"需要现场判定"的点**：请优先在**短输入 + eager** 下也确认 `skip_topk` 复用是否触发、以及 reuse 次数。如果 eager 下 reuse 次数 > 0 且精度正常，说明这条路径不是唯一原因（还要看 §2.2/§2.3）；如果 eager 下 reuse 次数 == 0 而 graph 下 > 0，则基本锁定。

**建议改法（用于验证，不是最终修复）**——把复用条件加严到"可证明同一批 token"：

```python
can_reuse_owner_plan = (
    skip_topk
    and owner_layer_id is not None
    and layer_id > owner_layer_id
    and self.fused_overlap_plan_topk == self.topk
    and self.fused_overlap_plan_num_tokens == num_tokens
    and owner_map is not None
    # 【验证用】再加一道"同帧"闸门，任一不满足就退回重跑 planner：
    and self.fused_overlap_plan_frame_id == frame_id            # 新增：每个 forward step 自增
    and self.fused_overlap_plan_req_ids_hash == req_ids_hash      # 新增：当帧 req_ids 的哈希
)
```

或**最快的一刀切验证**：临时让 `can_reuse_owner_plan` 恒为 `False`（强制每层重跑 planner），跑短输入图模式。**若复读消失 ⇒ 本条确诊**。代价是 planner 多跑几次（性能变差，不影响正确性）。

**打点建议**：在 `can_reuse_owner_plan` 为真的分支里打印
`layer_id / owner_layer_id / num_tokens / fused_overlap_plan_num_tokens / 是否发生 copy`，
并在 `publish_plan` 与复用分支各打一次 `plan_storage` 的 checksum（如前 64 个 int16 的哈希），比对"发布内容 == 消费内容"。

### 2.2【P0】D3 的描述符刷新时序 + "零有效行"的静默写

**子问题 A：host callback 与相邻拷贝的完成序**

`_prepare_current_kv_index_copy_descriptors`（`:1532-1563`）三步：

```python
self.d2h_slot_mapping_cpu[:token_count].copy_(slots, non_blocking=True)          # (A) D2H（异步）
_sparse_kv_ops().sparse_kv_enqueue_current_kv_index_copy_descriptors(...)        # (B) 挂 host callback
self.d2h_src_idx_npu.copy_(self.d2h_src_idx_cpu, non_blocking=True)              # (C) H2D（异步）
self.d2h_dst_idx_npu.copy_(self.d2h_dst_idx_cpu, non_blocking=True)
self.d2h_index_count_npu.copy_(self.d2h_index_count_cpu, non_blocking=True)
```

(B) 内部（`csrc/torch_binding.cpp:2688-2711`）用裸 `aclrtLaunchHostFunc(stream, callback, payload)` 把回调挂到当前流；
回调在**图重放时**重新执行 `build_current_kv_index_copy_descriptors`，该函数**直接读 `slot_mapping.data_ptr<int64_t>()`**。

**对照物（同一份代码里另一条已验证可用的 host 回调路径）**：非 fused 的 `onload_topk_kv`（`:1742-1752`）用的是

```python
torch_npu.npu._subscribe_report(current_compute_stream)      # ← 多了一步"订阅上报"
torch_npu.npu._launch_host_func(current_compute_stream, self._onload_topk_kv_cpu, args)
```

`_subscribe_report` 的缺席意味着：**没有任何机制保证"重放时 (B) 的 host 回调"与"(A)/(C) 的非阻塞拷贝"之间的先后**。若 (B) 读到未完成的 (A)，`dst_idx` 指向**上一 step 的 slot** ⇒ 当前 token 的 K/V 写到旧位置 ⇒ 下一步当作历史 token 从 host 读出错误 K/V ⇒ 复读。

**验证**：在 C++ 回调里打印 `count` 与前若干个 `src_idx/dst_idx`，与当帧 `slot_mapping` 逐 step 比对。若发现"写进去的是上一 step 的 slot"，确诊。
**建议改法**：把 (B) 换成与 `onload_topk_kv` 同款的 `_subscribe_report + _launch_host_func`；或在 (A) 之后、挂 callback 之前插入一次显式同步（图捕获下用 event + `wait_event`，eager 下直接 `torch_npu.npu.synchronize()` 做对照）。

**子问题 B：`num_copies == 0` 时会做一次"多余的 slot 0 写入"**

`build_current_kv_index_copy_descriptors`（`csrc/torch_binding.cpp`，PR2 新增）：

```cpp
if (num_copies > 0) {
    // padding 到 max_num_tokens：用最后一条合法项重复填充 → 形状稳定且幂等
    for (int64_t i = num_copies; i < payload->max_num_tokens; ++i) {
      src_idx[i] = last_src;  dst_idx[i] = last_dst;
    }
} else {
    std::fill_n(src_idx, payload->max_num_tokens, 0);
    std::fill_n(dst_idx, payload->max_num_tokens, 0);   // ← 全 0
}
count[0] = num_copies;
```

而**设备侧的写回并不读 `count`**（`_offload_new_kv_via_index_copy` 捕获分支，`:1619-1631`）：

```python
flat_host_k.index_copy_(0, self.d2h_dst_idx_npu, k_rows.index_select(0, self.d2h_src_idx_npu))
```

⇒ 当 `num_copies == 0` 时，会把 **host KV 的 row 0 覆盖成当前 K/V 的 row 0**。如果 host 池的 row 0 属于某个正在被使用的请求，就**静默破坏了它的第一个 token**。

**这一条在什么条件下会真的触发？** `_offload_new_kv_via_index_copy` 在 `token_count == 0` 时已提前 `return`（`:1592-1593`），所以只有"有 token 但**全部 slot 非法**"（`slot < 0` 或 `slot >= num_slots`）才会走到。短输入 + 图模式下 pad（填充）到静态形状时，**padding 出来的 token 其 slot 常为负**；若某帧恰好"真实 token 数极少、且 pad 行占多数"，虽然 `num_copies>0`（padding 分支沿用最后一条合法项，是幂等的、安全），但**只要某帧 `num_copies==0`，就会发生上面那次多余写**。

**验证**：在 `build_current_kv_index_copy_descriptors` 的 `else` 分支加计数与告警，跑短输入图模式看是否出现。
**建议改法**：`else` 分支把 `src/dst` 填成"**无害**值"而不是 0。最稳的是让设备侧也读 `count`（例如先 `index_copy_` 再 `masked_fill_`，或用 `count` 做边界），退一步可把 `dst_idx` 填一个**不在 host 池里但仍合法**的哨兵值（例如 `capacity-1` 且该 slot 永不分配），避免踩到真实数据。

**子问题 C：MTP 层级复用描述符的假设**

`:1379-1384`：

```python
prepare_index_copy_descriptors = True
if not has_prefill and k is not None and v is not None and self.use_fused_overlap:
    layer_id = self._get_offload_layer_id(layer_name)
    self.current_kv_by_layer[layer_id] = (k, v)
    prepare_index_copy_descriptors = layer_id == 0     # 只有第 0 层刷新描述符
```

假设"一个 forward step 内所有层共享同一个 `slot_mapping`"。GLM-5.2 默认带 MTP（`mtp_layer_id = num_layers-1`，`:737`），投机解码时 `decode_width = 1 + num_spec_tokens` ⇒ `max_num_topk_rows = min(max_num_tokens, max_num_reqs * decode_width)`（`:551-557`）。
**验证**：关闭 speculative decoding / MTP 跑一遍短输入图模式，看复读是否消失。

### 2.3【P1】D1 + Mooncake 存储侧：写 NPU 可寻址 host VA 的可见性

**机制（后端独有、eager 不敏感、graph 被放大）**

Mooncake 段的 K/V 视图来自 `mooncake_host_pool.py:194-213` 的 bump 分配：

```python
tensors.append(self.region.tensor.narrow(0, start, int(size)))   # int8 字节视图
```

各层的 bf16 K/V 视图是"同一块 host 物理内存上的不同类型切片"。`index_copy_` 写它、融合算子读它。
底层是 `mmap + HostRegister`（`allocate_mooncake_host_region:115-131`），并**自动置位 `VLLM_ASCEND_SKIP_MIGRATEPAGES=1`**（`:132-133`）。

两个后端在此处的本质差别：
- MemFabric：页面由 MemFabric 的 VMM 管理，设备可寻址性由它自己建立，写路径是 `offload.sparse_copy`（**MemFabric 自己的拷贝原语，它知道该怎么 flush**）；
- Mooncake：页面是 POSIX shm + HostRegister，写路径变成 torch 的 `index_copy_`（**torch 并不知道这块内存同时还要被"远端 RDMA 写"和"本端算子读"**）。

⇒ 这里存在平台级的一致性/可见性敏感点，而且**恰恰只在 D3 生效时才出现**（MemFabric 不走 `index_copy_`）。表现是"偶发读到旧值"，与"复读"这种持续性精度崩坏不完全一样，所以列为 P1。

**验证（都很便宜，建议尽早做）**

1. 把 `VLLM_ASCEND_SKIP_MIGRATEPAGES` 显式 `export 0`（不跳过 migratepages）与 `export 1` 对比。
   注意：PR1 的自动置位发生在 `initialize_kv_cache` 阶段，**晚于首次 `bind_cpus`**（详见方案解析 §4.2），所以必须**启动前 export** 才能生效。
2. 在 `index_copy_` 之后、`wait_for_current_kv_writeback` 之前插入一次强制 `torch_npu.npu.synchronize()`（临时、只做验证），看复读是否消失。
3. 对同一块 host 视图做"写后立即读回"自检：写若干 slot，再从另一个 stream/另一端读回，比对内容。

## 3. 问题 2（长输入 100k/1M → 乱码）的候选根因

长输入与短输入**不是同一类缺陷**（前者是"地址/容量/换页"，后者是"时序/计划内容"），请分开定位。以下是长输入**才会真正触发**的边界。

### 3.1【P1】`max_num_topk_rows` 与 plan 的行上限

```
max_num_topk_rows = min(max_num_batched_tokens, max_num_seqs * decode_width)   # :554-557
max_d2h_index_copy_tokens = max_num_topk_rows                                  # :558
```

plan 的 `num_tokens` 必须 ≤ 这个值，而 `_validate_fused_overlap_external_plan_inputs` 会硬校验（`:1992-1996`）。**长输入本身不直接抬高 `num_tokens`**（decode 每步 token 数由 batch 决定），但：

- `100k/1M` 请求**首次进入 decode 的那一步**，`num_computed_tokens` 很大，`visible_seq_lens` 也是 1M 量级；
- `selection_kv_block_status` 的 `row_capacity = max(max_num_topk_rows, num_tokens)`、以及 `full_kv_actual_seq` 等一维张量都按 1M 量级传值；
- `block_table_cpu` / `block_table_expanded_cpu` 的列数是 `ceil(max_model_len / block_size)`（`:570-582`）——1M / 64 = 16384 列，**在 int32 下安全**。

⇒ 这里没有发现溢出（`lru_*_workspace` 全是 `int32`；`lru_token_mark_workspace` 是 `[threads, max_model_len]` 的 int32，1M 也安全）。**结论：int16/int32 溢出不是长输入乱码的原因**（`membership map` 的 int16 只存"槽位号"和 marker，槽位 ≤ `topk_buffer_size` 默认 4096，远低于 32767）。

### 3.2【P1】host 池容量：`num_blocks × block_size` 与 `dram_size_per_dp_GB`

- host 池规划：`planned = num_blocks × Σ host page_size + n_host_specs × 3 × 2MiB`，超 `dram_size_per_dp_GB` 直接抛错（`:587-596`）——这是**响亮失败**，不是静默错。
- 但**下游有静默路径**：`_offload_new_kv_via_index_copy` 对 `slot >= num_slots` 是**静默丢弃**（C++ 过滤，不打印）；PR2 的 `_offload_new_kv_on_current_stream` 对 `token_count > max_num_tokens` 才报错。
  ⇒ 若 host 池的 token 容量与实际使用不匹配（例如 `num_blocks` 与实际分配的 block 数不一致），会**静默丢数据**，长序列下表现得像"远处的 KV 全错"⇒ 乱码。

**验证**：把 §2.2 子问题 B 里那个计数器也用在"被过滤掉的 slot 数"上；同时打印 `num_blocks`、`num_slots`、`num_tokens`、`max_num_topk_rows` 四个值在 100k 与 1M 下的实际数目。

### 3.3【P1】`num_blocks` 与实际 block 数的映射（PR3 侧引入）

PR3 的 `DsaCacheLayout` 带 `capacity`，`build_component_read` 会校验 `destination_ids[...] >= local.capacity`（`mooncake_dsa_transfer.py:218-221`）。
D 侧 `_build_dsa_local_layouts` 用 `self.num_blocks = self.kv_cache_config.num_blocks`（`mooncake_connector.py:3500`），而 **P 侧**用的是 P 自己的 block 表与 P 的 `block_size`（`dsa_main_block_size`）。
⇒ 长请求跨越更多 block 时，**任何一侧的 block 数与对方理解不一致**都会让"第 N 块"落到错误偏移。这类错位在短输入（几块）时几乎不可见，**在 100k/1M（成百上千块）时必然暴露**——这就是"短输入 OK、长输入乱码"最典型的形态。

**验证**：打开 `vllm_ascend` DEBUG 日志，抓 `DSA local layouts ready decode_rank=... indexer_components=... main_components=...` 与 `DSA built transfer plans ... token_range=[a,b)`，检查：
- `local.capacity`（= `num_blocks`）在 P/D 两侧是否一致；
- `token_range` 是否覆盖了完整 prompt；
- 传输合并统计 `statistics`（`entries_before/entries_after`）是否合理（若 `entries_after` 异常大，说明块级切分碎得离谱，可能是块大小不匹配的表现）。
