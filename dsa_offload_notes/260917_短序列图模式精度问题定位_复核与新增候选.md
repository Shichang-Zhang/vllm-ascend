## 2. 主因为什么站得住（原文档缺失的关键一环）

原文档只论证到"写回在 save 流、op 在 compute 流、两者之间没有边"，但**没有证明"op 真的会去 host 池读本 step 刚写的行"**。补上这一段后，P0 从"合理推测"变为"可证的机制"。

### 2.2 planner 层：本 step 窗口内的 token **必然**是"负 plan"

`sparse_kv_offload.cpp` 的 `process_one_lru_resident_row`（`104-233`）：

```cpp
:167   // The speculative suffix may have been overwritten in the CPU KV pool.
       if (is_valid_lru_resident_token(token, max_token) && UNLIKELY(token >= stable_prefix_len)) {
           slot_to_token_row[slot] = -1; token = -1;      // ← 主动驱逐"本 step 窗口"内的缓存项
       }
:199   const int32_t assign_count = std::min(local_miss_count, evictable_count);
:210   const bool is_current_token = visible_seq_lens != nullptr && token == visible_seq_len - 1;
:216   encoded_plan_row[pos] = is_current_token ? (slot + 1) : -(slot + 1);
```

而窗口边界来自 Python：

```text
sfa_kv_offload.py:801  stable_prefix_lens = actual_seq_lengths_key_decode[:num_reqs] - decode_query_lens
                       → 每 token 的 stable_prefix_len = seq_len - q_len = 本 step 窗口起点
sfa_kv_offload.py:694-726  visible_seq_len(row i) = seq_len - q_len + i + 1
```

**推论（这是原文档结论的关键补强）**：

1. 本 step 窗口内的 token（含 draft 行）**不可能命中 LRU**（`:167` 主动驱逐，理由：投机后缀可能被重写）⇒ 行 i（i≥1）的 topk 若含本 step 更早的行 j，plan 必为**负数** ⇒ **必然从 host 池取数**；
2. 只有**本行自己的 token**（`token == visible_seq_len-1`）被特判为**正数**（pseudo-hit），由 `inject_current_kv_into_selection`（`sparse_kv_offload_manager.py:2786-2810`）用 `fused_plan_current_linear_slots_npu` 把本行 KV 直接注入 selection buffer ⇒ 不需要 host 读；
3. **代码里存在 `is_current_token` 这个特判，本身就是"topk 里会出现本 step 窗口 token"的直接证据**——否则这个特判没有存在意义。同理可推：本 step 更早的行也会出现在行 i 的 topk 中。

> 结论：原文档 §2.3 给的理由（"这些 token 之前从未被引用过"）不够准确，**真实原因是 planner 主动驱逐 + 只有本行自身 token 走 paired-copy 注入**；但"MISS ⇒ 必然 host 读"这个结论是对的。

**两个重要观察**：

- `use_side_stream` 里显式写了 `and not use_mooncake_index_copy`，说明作者**本意是"Mooncake 路径不要用 save 流"**；但内层 `_offload_new_kv_via_index_copy` 在 `capturing` 时又把流切回了 `current_kv_save_stream`。⇒ 更像**疏漏**而非有意取舍，这一点强化了 E1 是真 bug 的判断；

### 2.4 MTP 是必要条件 —— 可证，不是推测

`q_len == 1`（decode_width = 1）时，每行窗口内只有自己的 token（走 inject），不产生 host 读 ⇒ 竞态自然消失。故 E1 **要求 decode_width ≥ 2（MTP / spec-decode 开启）**，这与原文档"实验 1（关 MTP）"的预测方向一致，且现在有了代码级依据。

### 3.3 🔴 必须重开：标准分支的 MTP 层描述符刷新（图模式专有）

```text
标准分支  ea8b8c1  sparse_kv_offload_manager.py:1385-1386
```

### 3.4 🔴 必须正视：eager 侧仍有残余复读

`踩坑总结.md` 原文（末段）：

> "提交后大幅度增加精度稳定性，**图模式下偶发，非图模式下没有看到明显词语复读，但是及其偶发发生段落重复**。"

原文档 §0 把它转述为"非图模式基本正常"，并声称 P0"能完整解释三个症状"。但：

- P0 是**流时序**缺陷，eager 单流有序 ⇒ P0 修复后 **eager 侧不会有任何变化**；
- 因此 eager 的残余"段落重复"**必然来自另一个与流序无关的根因**（候选：plan 内容/4 层复用、静默丢键、Mooncake 存储可见性、host 池容量与槽位映射）。

⇒ 建议把文档标题/结论从"找到根因"改为"**找到图模式侧的主因，另有一个 eager/graph 共有的次要根因待查**"。

### 5.2 建议新增打点（一次覆盖三种假设）


### 8.7 性能影响与备选改法

- 修复 B/C 的代价：TP0 在进入 ready broadcast 前必须等自己的写回完成，因此每层的 planner（CPU OMP）不再与写回并行。写回数据量为 `max_d2h_index_copy_tokens × (512+64) × 2B`（量级几十 KB），影响应远小于直觉，但仍建议在长序列基线上对比一次 TPOT。
- 备选（若性能受影响）：Mooncake + capturing **完全不切 save 流**，即删掉 `_offload_new_kv_via_index_copy` 里的 `with torch_npu.npu.stream(self.current_kv_save_stream)`，让写回直接落在 compute 流上。这与 `use_side_stream` 中 `and not use_mooncake_index_copy` 的原意一致，语义上等价于修复 B，且**同时消掉 planner 串行化代价**。本次没直接这么做，是为了保持"只加同步边、不改写回位置"的最小形态、便于归因；可作为 §5.3 实验 3 的 A/B 项。
