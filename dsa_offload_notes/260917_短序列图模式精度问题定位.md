## 0. 结论摘要（TL;DR）

**找到一个能完整解释"图模式偶发、非图模式正常、短序列更明显"三个症状的时序缺陷（P0）**：

> **图模式下，当前 step 的 KV 写回（`current_kv_save_stream`）与融合算子读 host KV（compute 流）之间没有任何同步边。**
> 融合算子做 miss onload 时从 host 池取数，可能取到**本 step 刚要写入、还没写完**的行——
> 而 MTP（GLM-5.2 默认开启，decode_width > 1）下，**同一 step 内后面的 token row 合法地引用同 step 更早的 token**，
> 这些 token 的 KV 只存在于 host 池 ⇒ 必然竞态。

唯一的消费者侧等待 `wait_for_current_kv_writeback` 有两个致命限制：

1. **位置错误**：在 `fused_op(...)` **之后**才调用（`sfa_kv_offload.py:1026` 是 op，`:1028` 才 wait）；
2. **范围错误**：仅 TP0 执行（`self.tp_rank == 0` 门槛），TP1-7 从不等任何写回流。

**为什么 eager 正常**：eager 分支的 index_copy_ 写回直接在 current stream 上、且在 fused op 之前执行，同流天然有序；TP0 的 ready broadcast 也与写回同流有序。**图模式下写回被切到 save 流、broadcast 是独立图节点，两条边全部缺失**——这正好解释 `ea8b8c1`（TP0 d2h 后加 broadcast）"大幅改善精度稳定性、但图模式仍偶发、非图模式基本正常"的观察：broadcast 只修了**跨 step 的 TP 间可见性**，没有修**同 step 的 save流 ↔ fused op 边**。

## 1. 前置事实：图模式 replay 的真实语义（已核实）

`vllm_ascend/compilation/acl_graph.py:133-264` 的 `ACLGraphWrapper.__call__`：

| 阶段 | 行为 |
| :--- | :--- |
| warmup / profile（`runtime_mode == NONE`） | `return self.runnable(...)` —— **eager 执行**，`forward_context.capturing=False` |
| capture（`entry.aclgraph is None`） | `forward_context.capturing=True` + `with torch.npu.graph(aclgraph): self.runnable(...)` —— Python 前向跑一遍并录图 |
| **replay（稳态）** | `entry.aclgraph.replay()` —— **Python 前向完全不重跑**，只有捕获进图的设备节点 + host callback 重放 |

推论（用于排除干扰项）：

1. replay 时 Python 不执行 ⇒ eager planner 路径（`capturing=False` 分支）在 replay 时**不会跑**，LRU planner 靠捕获进图的 host callback（`aclrtLaunchHostFunc` + `aclmdlRI` 生命周期 payload，`sparse_kv_offload.cpp:955-1020`）每帧重放刷新——**不存在 planner 双重执行**；
2. `capturing`（capture 才为 True）与 `_in_graph_runtime()`（capture+replay 都为 True）的混用只影响**捕获时选哪条分支**，replay 时无 Python 代码在跑，故该混用本身不直接产生 replay 期 bug（`260916_DSA精度问题定位分析.md` §5.3 的 P2 项在此分支上降级）；
3. FULL 模式 replay 前有 `torch.npu.current_stream().synchronize()`（`acl_graph.py:260-262`）⇒ 相邻两次 replay 全串行，跨 replay 的 pinned buffer 复用无竞争；
4. 图模式 slot_mapping padding 为 **-1**（`model_runner_v1.py:2963-2967`）⇒ C++ 描述符构建会过滤 pad 行，pad 不会写脏 slot。

## 2. 主因（P0）：save 流写回与 fused op 读 host KV 无同步边

### 2.1 代码事实（逐字核实）

**写回侧**——`sparse_kv_offload_manager.py:1811-1830`（`_offload_new_kv_via_index_copy`，capturing 分支）：

```python
if capturing:
    if prepare_descriptors:                      # layer 0 / MTP 层刷新描述符
        self._prepare_current_kv_index_copy_descriptors(...)
    current_kv_ready = torch_npu.npu.current_stream().record_event()   # compute → save 方向
    with torch_npu.npu.stream(self.current_kv_save_stream):
        self.current_kv_save_stream.wait_event(current_kv_ready)
        flat_host_k.index_copy_(0, self.d2h_dst_idx_npu,
                                k_rows.index_select(0, self.d2h_src_idx_npu))
        flat_host_v.index_copy_(...)
    return                                        # ← 没有任何 save → compute 的 event
```

**消费侧**——`sfa_kv_offload.py:991-1028`（`_execute_fused_overlap_offload_decode`）：

```python
manager.inject_current_kv_into_selection(...)      # compute 流
attn_output = fused_op(**fused_inputs)             # :1026  ← fused op 在这里（miss 时从 host 池 H2D 取数）
manager.wait_for_current_kv_writeback(...)         # :1028  ← 唯一的等待，在 op 之后！
```

**唯一的等待**——`sparse_kv_offload_manager.py:2816-2818`：

```python
def wait_for_current_kv_writeback(self, capturing: bool = False) -> None:
    if self.use_fused_overlap and capturing and self.tp_rank == 0:   # ← 仅 TP0
        torch_npu.npu.current_stream().wait_stream(self.current_kv_save_stream)
```

全仓 grep 确认：`current_kv_save_stream` 的消费者侧等待**只有这一处**（共 8 处引用，其余全是定义与生产侧）。

### 2.2 缺失的同步边（图模式捕获 DAG 视角）

```
一层内的捕获 DAG（FULL 图，整段 decode 前向一张图）：

compute流: exec_kv 计算 k/v ──event──► save流: D2H slots → host cb → H2D 描述符 → index_copy_ 写回 host 池
                     （唯一的边，方向：compute → save）
compute流: plan 发布(fused_plan_stream 子图) → inject → fused_op（读 host KV 做 miss onload）
                     ↑ 与 save 流写回之间【无边】
compute流: fused_op 之后 → wait_stream(save流)   （仅 TP0；太晚）
compute流: ready broadcast（ea8b8c1 引入）        （与 save 流写回【无边】）
```

| # | 缺失的边 | 受影响者 | 后果 |
| :--- | :--- | :--- | :--- |
| E1 | save流写回 → 本层 fused_op | **TP0 自己也中招** | MTP 下同 step 跨行 host 读竞态 |
| E2 | save流写回 → ready broadcast | **TP1-7** | broadcast 放行时 TP0 的写可能还没落 |

### 2.3 为什么恰好是"短序列 + MTP + 图模式"触发

1. **同 step 跨行引用是 MTP 的合法行为**：decode_width > 1 时，一个 forward step 处理同一请求的多个 token（row 0..w-1）。row i 的 topk 由 indexer 打分产生——indexer cache 在每层 prolog 已包含本 step 的 token，而**最新 token 打分最高，几乎必然入选 topk**。
2. **这些 token 的 KV 只在 host 池**：token j<i 是本 step 新生成的，之前从未被引用过 ⇒ membership map 里必是 MISS ⇒ 融合算子必从 host 池 H2D 取数 ⇒ 取的正是本层 `exec_kv` 刚在 save 流上发起写入的那一行。
3. **为何 eager 无此问题**：eager 写回在 current stream（`manager:1854-1868`，无 stream 切换）、在本层 op 之前，同流串行 ⇒ 有序。eager 下 TP0 的 ready broadcast 也在同一流上排在写回之后 ⇒ TP1-7 被正确卡住。**Eager 全有序 / 图模式两条边全缺**——与"非图模式没有明显词语复读、图模式偶发"完全吻合。
4. **为何短序列更明显**：
   - 短序列时 topk（如 2048）覆盖整个历史的比例大，同 step token 入选 topk 且为 MISS 的概率接近必然；
   - 短序列下每 step 的 miss 总量少，被污染的行在 topk 中占比高，单行污染直接决定该步注意力输出；
   - 短序列 + 小 batch 是图模式 pad bucket（1/2/4/8…）的主要使用区，同一条捕获图高频重放，竞态窗口反复出现 ⇒ "偶发"。
5. **为何与 `ea8b8c1` 的观察一致**：broadcast 修复的是"跨 step TP1-7 读 TP0 上一步写回"的可见性（跨 step 场景实际靠 TP0 图内捕获的 wait-save 链 + 流序兜底），而**同 step（E1）与图模式跨 rank 同步（E2）两条边始终缺失** ⇒ 精度"大幅改善但仍图模式偶发"。

### 2.4 佐证：跨 step 场景为什么反而"碰巧"是安全的

- TP0 图内在每层 op **之后**捕获了 wait-save（`:1028` 在 capture 时执行、被录进图）⇒ TP0 的 compute 流在层 L+1 的任何节点之前已等完层 L 的全部 save 流写 ⇒ TP0 的下一 step broadcast（也在 compute 流）必然晚于上一步所有写 ⇒ 跨 step 的 TP1-7 读被这条链兜住；
- 但**同 step**（MTP）场景下，op 与写回在同一层内、wait 又排在 op 后 ⇒ 完全无保护。

> 换句话说：现在的代码"每层 op 之后才等本层写回"的设计，只在 decode_width == 1（同 step 没有人读本 step 的 host 写）时是安全的；MTP 一开就是漏洞。

## 3. 次要疑点（非主因，但建议一并处理）

| # | 问题 | 位置 | 说明 |
| :--- | :--- | :--- | :--- |
| S1 | 描述符 host 回调用裸 `aclrtLaunchHostFunc`，与前置 `non_blocking=True` 的 D2H（slot_mapping）之间无显式联锁；非 fused 路径（`onload_topk_kv`）用的是 `_subscribe_report + _launch_host_func` 配对，两条路径不一致。若所在 CANN 版本的 host-func 节点不保证晚于前置 D2H 的主机可见性，回调会读到**上一 step 的 slot** ⇒ 当前 token KV 写到旧槽位 ⇒ 复读 | `sparse_kv_offload.cpp:629-656` vs `sparse_kv_offload_manager.py:2149-2159` | 平台级疑点（同 260916 文档 H2），建议做一次对照实验 |
| S2 | `num_copies == 0` 时描述符 src/dst 全填 0，而设备侧 `index_copy_` 不读 `count` ⇒ 静默覆写 host 池 row 0。decode 真实 token 槽位必合法，正常 decode 不会触发，但属防御性缺陷（且与 260916 文档 H3 一致） | `sparse_kv_offload.cpp:550-553` | 建议改成无害哨兵值或让设备侧读 count |
| S3 | capturing 分支不检查 planner 状态（eager 分支检查 `fused_plan_status_npu` 并抛错）；replay 时 Python 不跑 ⇒ planner（host callback 内）一旦失败，图模式会**静默用旧 plan** ⇒ 无日志的精度劣化 | `sparse_kv_offload_manager.py:2446-2558`（无 status 校验）vs `:2599-2607`（eager 有） | 建议在 plan 控制字里带上 status、算子侧或下一帧校验 |

**本轮已排除的候选**（避免重复排查）：

- H1（跨层 plan 复用内容陈旧）：本分支 `fused_overlap_plan_membership_map = selection_membership_map`（`:2557/:2611`），而所有层共享 manager 分配的同一张 membership map（`allocate_fused_overlap_membership_map` 有 `if ... is not None: return` 幂等返回，`:819-826`）⇒ `data_ptr()` 恒相等 ⇒ 复用分支的 `copy_` 恒空转，**MemFabric 与 Mooncake 一致**，260916 文档所述"两后端行为分裂"在该分支不成立；
- 图模式 pad 行写脏 slot：padding = -1（`model_runner_v1.py:2967`），C++ 过滤（`sparse_kv_offload.cpp:535`）；
- planner 双重执行：replay 时 Python 不重跑（§1）；
- MTP 层描述符不刷新：decode-only 分支已修（`prepare_index_copy_descriptors = layer_id in (0, self.mtp_layer_id)`，`:1424`，对应踩坑总结 #3）。

## 4. 验证实验（无需真机即可先准备，按信息量排序）

```text
实验 1（最便宜、最快证伪）：关闭 MTP / speculative decoding，跑短序列图模式
  └─ 复读消失 ⇒ 锁定 E1（同 step 跨行 host 读竞态）；仍在 ⇒ 转 S1/H2

实验 2（直接验证修复）：sfa_kv_offload.py:1028 的 wait 移到 :1026 fused_op 之前，
  并在写回后加 save_stream.record_event() + broadcast 前 current_stream.wait_event(...)
  └─ 复读消失 ⇒ E1/E2 确诊

实验 3（定位机制）：图模式临时去掉 save 流（capturing 分支不切流，写回直接放 current 流）
  └─ 复读消失 ⇒ 确认竞态全部来自 save 流时序缺口

实验 4（S1 平台疑点）：把 enqueue_current_kv_index_copy_descriptors 换成
  _subscribe_report + _launch_host_func 同款配对，对比图模式精度
```

打点建议：在 `_offload_new_kv_via_index_copy` capturing 分支记录（save 流写回完成事件号、当帧 slot 首尾值），在 fused op 前后各 dump 一次 miss 行的 host KV checksum；出现复读时比对"被读行 checksum == 本帧应写入值？"即可当场抓住"读到未写完数据"。

## 5. 建议修复（若实验命中）

1. **E1（语义正确性，无条件应修）**：`wait_for_current_kv_writeback(capturing)` 移到 `fused_op` **之前**（`sfa_kv_offload.py:1026` 前）。代价是损失"写回与算子重叠"的一点点收益——但该重叠本就只对 decode_width==1 安全；
2. **E2（跨 rank 正确性）**：capturing 分支写回后 `self.current_kv_save_stream.record_event()`，`offload_new_kv` 的 ready broadcast 前 `current_stream.wait_event(...)`，使 broadcast（进而 TP1-7 的 op）真正有序于 TP0 写回；
3. **S1**：host 回调改用 `_subscribe_report + _launch_host_func` 配对，或 (A) 前插入 event 联锁；
4. **S2**：`num_copies==0` 时填无害哨兵（而非 0），或设备侧尊重 count；
5. **S3**：plan 控制字带 status，图模式消费侧校验并告警。
