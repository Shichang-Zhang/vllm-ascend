## 2. 本次修了什么（4 处，全部围绕"共享 Host 池的写后读顺序"）

### 修复 A（P0-新）：MTP 层也刷新 index_copy 描述符

| 项 | 内容 |
| :--- | :--- |
| 文件 | `vllm_ascend/distributed/kv_transfer/sparse_kv_offload/sparse_kv_offload_manager.py`（`offload_new_kv`） |
| 改动 | `prepare_index_copy_descriptors = layer_id == 0` → `layer_id in (0, mtp_layer_id)`（`-1` 表示没有独立 MTP 层） |
| 问题 | 图模式下 KP 写回走 descriptor 路径，而描述符只在 layer 0 生成。MTP 层的 `slot_mapping` 若与普通层不同，MTP 的 K/V 就会被写到**错误的 Host 行**，正确行永远没写；eager 路径直接用 `slots` 计算，不读描述符，所以**只有图模式受害** |
| 依据 | decode-only 分支的 `c806ec153` 已含同样修复，标准分支缺失（`git log -S "layer_id in (0, self.mtp_layer_id)"` 只命中该提交） |

### 修复 B：把等待写回从"算子之后"移到"算子之前"（原 P0 / E1）

| 项 | 内容 |
| :--- | :--- |
| 文件 | `vllm_ascend/attention/sfa_kv_offload.py`（`_execute_fused_overlap_offload_decode`） |
| 改动 | `manager.wait_for_current_kv_writeback(...)` 从 `fused_op(...)` 之后移到之前 |
| 问题 | 融合算子会把"不在 selection buffer 里"的 TopK 行**直接从共享 Host 池取数**（算子侧 `IsSelectionPlanUpdate(plan<0)` → `GetRealS2Idx`）。MTP 下这些行包含**本 step 更早的 token 行**（planner 依据 `token >= stable_prefix_len` 主动把本 step 窗口逐出 LRU，只有"本行自己的 token"走 inject 特判），而它们的 K/V 正在 save 流上异步写回 ⇒ 读到未写完/上一步的旧值 |
| 依据 | `IsSelectionPlanHit/Update` 见算子 `arch22/...service_vector_mla.h:1817-1847`、消费点 `:3211-3240`；planner 驱逐见 `sparse_kv_offload.cpp:167`、`is_current_token` 特判 `:210-222` |

### 修复 C：TP0 进入 ready broadcast 之前先 join 写回流（原 P0 / E2）

| 项 | 内容 |
| :--- | :--- |
| 文件 | 同 `sparse_kv_offload_manager.py`（`offload_new_kv`，ready broadcast 之前） |
| 改动 | broadcast 前插入 `self.wait_for_current_kv_writeback(capturing)` |
| 问题 | TP1-7 不写 Host 池，它们与 TP0 之间唯一的顺序信号就是这条 broadcast。原代码里 broadcast 与 TP0 的 save 流之间**没有任何边**（broadcast 在 compute 流、写回在 save 流），于是 TP1-7 被过早放行 |
| 注意 | 只有 TP0 会真正等待（`wait_for_current_kv_writeback` 内部有 `tp_rank != 0` 直接返回）；TP1-7 无需额外动作，它们被 broadcast 卡住即已有序 |

### 修复 D：写回是否"真的切过流"变成显式状态

| 项 | 内容 |
| :--- | :--- |
| 文件 | 同 `sparse_kv_offload_manager.py`（`__init__` / `_offload_new_kv_via_index_copy` / `wait_for_current_kv_writeback`） |
| 改动 | 新增 `current_kv_writeback_on_side_stream`；切流前置 `True`；等待条件由 `capturing and tp_rank==0` 改为 `tp_rank==0 and (capturing or 该状态位)` |
| 问题 | 原判断依赖调用方传入的 `capturing`。但 `exec_kv` 传的是 `_in_graph_runtime()`（capture **和** replay 都为真），而算子路径传的是 `forward_context.capturing`（只有 capture 为真）——两者不一致时会出现"写回切了流、消费侧却不等" |
| 兼容性 | 条件取"或"，对既有调用语义是**超集**（原来会等的场景仍然等），因此不改变既有行为，只补上漏等的情况 |

## 4. 刻意没动的东西（附原因与建议）

| 项 | 为什么不动 | 建议 |
| :--- | :--- | :--- |
| `num_copies == 0` 时描述符全填 0 ⇒ 设备侧覆写 host row 0 | 设备侧 `index_copy_` 不读 `count`，要真正修掉需要"让设备侧尊重 count"或用哨兵槽，属于 API/内存布局级改动，风险明显高于收益（decode 图模式下 `token_count` 恒 > 0，只有"有 token 但 slot 全非法"才触发） | 单独一个 PR：C++ `else` 分支填无害值 + 设备侧加 `count` 校验或 `masked_fill` 兜底 |
| plan 值为 0（`SELECTION_COMPACT_PLAN_INVALID`）的 miss 被算子直接跳过（`assign_count` 截断） | 这是"有界工作量"的设计取舍，不是 bug；但**丢的是最新、权重最大的键**，且无日志 | 加统计与告警（见 `260917_..._复核与新增候选.md` §5.2 A），先观测再决定是否改策略 |
| planner 在图模式下无 status 校验（host callback 为 `noexcept`） | 需要算子侧配合读控制字（改 kernel），超出本次范围 | 按原文档 S3 的方案：plan 控制字带 status，图模式消费侧校验并告警 |
| Mooncake 存储侧可见性（`SKIP_MIGRATEPAGES`、HostRegister 段被 NPU 核写） | 属平台级，需真机对照实验，代码改不动 | 实验：启动前 `export VLLM_ASCEND_SKIP_MIGRATEPAGES=0` 对照；`index_copy_` 后强制 `synchronize()` 对照 |
| eager 侧残余"极其偶发段落重复" | 与流序无关，本次 4 处改动**不会**影响它 | 按复核文档 §4 的 P1-新"静默丢键"与 plan 内容方向继续查 |

## 5. 性能影响与备选改法

- 修复 B/C 的代价：TP0 在**进入 ready broadcast 之前**必须等自己的写回完成，因此每层的 planner（CPU OMP）不能再与写回并行。写回数据量很小（`max_d2h_index_copy_tokens` 行 × (512+64)×2B，量级几十 KB），实测影响应远小于原文档担心的程度，但**仍建议在 100k/长序列基线上对比一次 TPOT**。
- 更彻底的备选（若性能受影响）：让 Mooncake + capturing **完全不切 save 流**，即删掉 `_offload_new_kv_via_index_copy` 里的 `with torch_npu.npu.stream(self.current_kv_save_stream)`，写回直接落在 compute 流上。这与 `use_side_stream` 里 `and not use_mooncake_index_copy` 的原意一致，语义上等价于修复 B，并且**同时消掉 planner 串行化的代价**。本次没有直接这么做，是为了让改动保持"只加同步边、不改写回位置"的最小形态，便于定位归因；建议作为实验 3 的 A/B 项。

### 6.2 打点（现有探针在图模式下是盲的，必须新增跨流打点）

```text

     （正=inject 注入 / 负=从 Host 池读 / 0=被丢弃）

     前 != 后  或  前 == 上一步的值  ⇒ 当场抓到读到旧数据
C. 记录 save 流完成事件与算子所在流的时间戳差，量化竞态窗口
D. replay 帧号 vs host callback 实际消费帧号（验证跨帧 pinned buffer 复用）
```
