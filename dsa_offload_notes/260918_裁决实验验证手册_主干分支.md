1. 本分支所有新探针由环境变量 `VLLM_ASCEND_SFA_ADJ_PROBE=1` 打开，输出在 **stderr**（C++ 侧异步 sink + Python `logger.warning`），每行前缀 `[SFA_ADJ_PROBE]`。

## 1. 背景：到底要验证什么

### 1.1 问题现场

| 项 | 值 |
| --- | --- |
| 模型 | GLM-5.2（MTP / 投机解码，`num_target_layers != num_layers`） |
| 并行 | TP = 8 |
| 部署 | PD 分离（prefill / decode 分开），decode 节点执行 ACL graph capture/replay |
| Host 池后端 | `host_backend=mooncake`（另有 MemFabric 作为差分对照） |
| 现象 | **短序列 + 图模式**下偶发精度问题；长序列另有结构性疑点（另案） |

### 1.2 机理假设 H1（实验 1 / E1 的对象）

```
compute stream :  ... planner --> inject -> [pre_join] --(wait_for_current_kv_writeback, 仅 tp_rank==0)--> [post_join] -> fused_sparse_attention -> ...
save stream    :  (writeback)  ... ACL graph capture/replay: flat_host_k.v.index_copy_ 被 fork 到 current_kv_save_stream
```

* fork 点：`sparse_kv_offload_manager.py::_offload_new_kv_via_index_copy`（Mooncake）与 `offload_new_kv` 的 `use_side_stream` 分支（MemFabric 图捕获路径），二者都设置 `current_kv_writeback_on_side_stream = True`。
* join 点：`wait_for_current_kv_writeback()`（`sparse_kv_offload_manager.py:2496`），**且开头有 `if not self.use_fused_overlap or self.tp_rank != 0: return`** —— 也就是说 **peer rank（tp_rank≠0）根本不执行 join**，它们只靠 TP ready 广播被"放行"。
* 因此：fork 出来的写回与同一步的读者之间**没有天然 happens-before**；TP0 靠 join 补，peer 靠广播补。若广播只是"TP0 到达"的信号而不是"数据已落地"的边，则整条链就断了。

### 1.3 为什么"同一步读者"确实会读 Host 池（依赖真实存在的证明链）

1. planner 会主动驱逐本步窗口 token：`sparse_kv_offload.cpp` 中 `token >= stable_prefix_len` ⇒ `slot_to_token_row[slot] = -1; token = -1;`。
2. 只有 **own token**（`token == visible_seq_len - 1`）拿到正 plan（`slot + 1`），其数据来自 `inject_current_kv_into_selection`（每行只有一行）。
3. 其余窗口位置拿到负 plan 或 plan = 0 ⇒ 算子必须走 `full_kv_cache`（= `k_caches_cpu[layer_id]`，与写回目标同一块内存）⇒ **读 Host 池**。
4. 只有 MTP（`q_len ≥ 2`）时，第 `i` 行的 topk 才可能包含第 `j<i` 行 ⇒ 才会出现"读本步刚写的行"。`q_len == 1` 时窗口里只有 own token，inject 已覆盖 ⇒ 不读 Host。

> **推论**：如果"同一步 Host 读"不存在，H1 整体不成立，应转向其它候选。这正是实验 0（planner 统计）要独立回答的问题。

### 1.4 待裁决的四个候选

| 编号 | 候选解释 | 用哪组探针裁决 |
| --- | --- | --- |
| E0 | "同一步 Host 读"是否真的存在、量级多大；是否有"静默丢 key" | `planner_stats` |
| E1 | 时序缺边：写出去了但读者先跑（或 join 不覆盖 peer） | `post_write` / `pre_join` / `post_join` / `pre_bcast` / `post_bcast` |
| E2 | MTP 层用了与 layer0 不同的 slot_mapping，导致写错行 | `slot_mapping_l0` / `slot_mapping_mtp` |
| E3 | MemFabric `sparse_copy` 是异步的，返回≠落地（用来解释"MemFabric 正常"） | `sparse_copy_landing` |
| E4 | 后端差分：Mooncake 设备视图 vs MemFabric 主机视图语义不同 | `host_kv_visibility_post_write/pre_join/post_join` 两后端对照 |

## 4. 五组实验（逐条）

> 通用前置：`VLLM_ASCEND_SFA_ADJ_PROBE=1`、图模式 capture/replay 已生效、每 rank 收一份 stderr。

### 实验 0 · 依赖规模与静默丢 key（`planner_stats`）

* **要回答**：同一步 Host 读到底存不存在？有多少？有没有"静默丢 key"？
* **操作**：短序列（复现问题的那组 prompt）跑图模式 decode；grep `stage=planner_stats`。
* **字段**：`values=[window_refs, window_loaded, window_dropped, dropped_misses]`
  * `window_refs`：本层 topk 中指向"本步**其它**窗口 token"的引用数（`token >= stable_prefix_len`、`token < visible_seq_len`、非 own token）。
  * `window_loaded`：其中拿到 LRU 驻留行、无需读 Host 的部分。
  * `window_dropped`：其中**没拿到任何 slot**、plan 保持 0 的部分 —— 算子只能读到 Host 池里当时的值。
  * `dropped_misses`：所有因"可驱逐槽位不足"被丢弃的 miss 数。
* **判定**：

| 观测 | 结论 |
| --- | --- |
| `window_refs > 0`（任何一层任何一步） | **依赖真实存在**；E1 的前提成立，继续做实验 1 |
| `window_refs == 0` 全程 | 该 workload 下同一步不读 Host ⇒ **H1 不成立**，应转向长序列结构性疑点/其它候选 |
| `window_dropped > 0` | 存在"静默丢 key"路径（plan=0 ⇒ 读 Host 现值），这是**独立于时序**的第二类错误来源 |
| `dropped_misses > 0` | LRU 驱逐压力出现，长序列更需关注 |

* **陷阱**：`planner_stats` 是被**覆盖写**的（每次 planner 调用先把 4 个槽清零），所以看到的是"那一次调用"的量；按 `layer_id` 分辨。它受抽样限制（§6.1），但 `window_refs>0` 这种量级会持续出现，不必要求"每步都有"。

### 实验 1 · 时序裁决（核心，E1）

* **要回答**：写回 fork 出去后，读者是否在数据落地前就读了 Host；join 是否覆盖读者；peer 是否只靠广播被放行。
* **操作**：短序列图模式 decode（Mooncake），grep 五个 `host_kv_visibility_*` 阶段。
* **判定矩阵**（`n>0` 表示"该时刻仍有 n 行没落地"）：

| `post_write` | `pre_join` | `post_join` | 含义 |
| --- | --- | --- | --- |
| 0 | 0 | 0 | 本步没有未落地行（写回已被 join 或本步无需写） ⇒ 该步不能作为证据 |
| **>0** | 0 | 0 | **join 是有效边**：写回确实滞后过，且 join 补齐了。E1 的"缺边"成立于 join 之前；若此时仍出问题，说明**故障发生在 join 之前/之外的读者** |
| **>0** | **>0** | 0 | join 在 TP0 上生效，但 `pre_join` 时刻（即 fused op 之前那一刻）仍是脏的 ⇒ 只要 join 位置正确就安全 |
| **>0** | **>0** | **>0** | **join 没有覆盖该 rank 的读者** ⇒ 真实缺边（TP0 上说明 join 位置/条件错；peer 上说明广播没兜住） |
| 0 | 0 | >0 | 异常组合（写回更晚落地）⇒ 检查是否 `layer_id` 对应不同层 |
| 任何非零 | — | — | 只要出现 `post_write>0`，就用 `frame` 把同一 step 的 5 条记录串起来做时间线 |

* **`pre_bcast` / `post_bcast` 的专用判据**（peer rank 尤其重要，因为 peer 不执行 join）：

| rank | `pre_bcast` | `post_bcast` | 含义 |
| --- | --- | --- | --- |
| peer（≠0） | >0 | **0** | 广播有效：TP0 已把数据落地并把 peer 正确放行 ✅ |
| peer（≠0） | >0 | **>0** | **广播只是"到达信号"，不是"落地"的边** ⇒ 这是 peer 侧真实缺边（E1 的第二种形态）|
| TP0 | 任意 | 0 | TP0 自身由 join 保证，`pre_bcast` 等价于 `post_join` |

> ⚠️ **peer 上 `pre_bcast > 0` 是正常的**（peer 从不 fork 写回，join 对它是空操作），只有 `post_bcast > 0` 才是问题。这条最容易误判。

* **与"实际问题"的关联**：如果 `post_bcast > 0` 与你会话中出现精度异常的时间点（step 数）能对上，则 E1 成立。

### 实验 2 · MTP 与 layer0 的 slot_mapping 是否不同（E2）

* **要回答**：图路径复用 layer0 的 descriptor 是否会导致 MTP 层写错 Host 行。
* **操作**：捕获期关注 `stage=slot_mapping_l0` 与 `stage=slot_mapping_mtp` 两类的 `hash`（也可看 `values=[...]` 的前 8 个槽号）。
* **判定**：

| 观测 | 结论 |
| --- | --- |
| 同一 step 内 `hash(l0) != hash(mtp)` | **MTP 层确实使用不同映射** ⇒ descriptor 刷新（本分支已包含的修复）是**必要的**，E2 成立 |
| `hash(l0) == hash(mtp)` | 该 workload 下两映射相同 ⇒ 刷新是"防御性"而非必需（不能据此说该修复无效，只是在本 workload 下不改变结果） |

* **陷阱**：`slot_mapping` 是逻辑缓冲区引用，replay 前由 runner 填充；请确保在 **capture 期**与 **replay 稳定期**都各取一段样本。

### 实验 3 · MemFabric `sparse_copy` 完成语义（E3）

* **要回答**：`offload.sparse_copy` 返回时数据是否已经落到 Host 池（用来解释"MemFabric 一直正常"）。
* **操作**：`host_backend=memfabric`，**eager 模式**跑 decode（该探针只在 `not capturing` 时挂载）；grep `stage=sparse_copy_landing`。
* **判定**：

| 观测 | 结论 |
| --- | --- |
| `immediate_mismatch=k:0/v:0` 但 `after_sync_mismatch>0` | 计数/掩码逻辑有问题，实验无效 |
| `immediate_mismatch=0` | 返回即落地 ⇒ **"稀疏写是异步的、所以 MemFabric 正常"这一解释 (a) 被否定**（应去找别的解释） |
| `immediate_mismatch>0` 或 `elapsed_ms` 接近 0 | 返回时确实未落地 ⇒ 解释 (a) 成立，MemFabric 的"正常"只是时序巧合 |

* **注意**：`immediate_mismatch` 是**主机侧直接读共享内存**，不等待任何流，所以它测的正是"返回时刻"的可见性，不受探针自身的同步影响。

### 实验 4 · 后端差分（E4）

* **要回答**：两条后端通路是否在"谁能看到 Host 行"上语义不同，从而解释"Mooncake 坏 / MemFabric 好"。
* **操作**：同一 workload 分别用 `host_backend=mooncake` 与 `memfabric` 各跑一轮，比较：
  * Mooncake：`host_kv_visibility_*`（设备视图，值来自 NPU 上直接比较，即"算子将会读到什么"）；
  * MemFabric：`host_kv_visibility_hostview_*`（CPU 共享内存视图，`mismatches=n/m first_bad_token=`）。
* **判定**：

| 观测 | 结论 |
| --- | --- |
| Mooncake 非零、MemFabric 全零（相同 step 段） | 设备视图比主机视图"更早可见"或写回顺序不同 ⇒ 需要按后端分别加固 |
| 两者都非零 | 缺边是通用的 ⇒ E1 与后端无关 |
| MemFabric 也偶发非零 | "MemFabric 一直正常"是**概率/负载**造成的假象，两个后端都需要修 |

$rec = Select-String -Path run_r0.err,run_r0.out -Pattern '\[SFA_ADJ_PROBE\] stage=(host_kv_visibility_\w+|planner_stats)' | ForEach-Object { $_.Line }
$rec | ForEach-Object {

    [pscustomobject]@{ stage=$Matches[1]; frame=[int]$Matches[2]; t_us=[long]$Matches[3]; layer=[int]$Matches[4]; obs=$Matches[5] }

## 6. 已知局限与陷阱（务必先读）

### 6.1 采样规则（最容易踩）

C++ sink 只在下列条件之一成立时打印：**计数非零** ∥ `call <= 4` ∥ `call` 是 2 的幂 ∥ `call % 64 == 0`。

* 含义：**非零（异常）永远打印**；零值（正常）大部分被丢掉。
* 后果：不要用"某 stage 没有出现"推断"该 stage 从未执行"；要用 `stage=... values=[0]` 是否出现来判断。若需要完整轨迹，可临时把 `call % 64` 改小（如 `call % 4`），但会显著放大日志量。

### 6.2 `frame` 的语义边界

`frame` 由 `post_write`+`layer_id==0` 的记录推进。由于 `post_write` 记录与 save 流上的写回、以及 `fused_plan_stream` 上的 `planner_stats` 属于不同流，**回调的到达顺序不保证**：某个 step 的 `planner_stats`/写回记录可能被打到上一帧或下一帧。**同帧内的判定不受影响**（我们有 `t_us` 兜底）；跨帧对齐请以 `layer_id==0` 的 `post_write` 锚点为准。

### 6.3 计数器清零语义

设备视图计数器在 `layer_id==0 && stage==post_write` 时整体清零，所以每个 `values=[n]` 描述的是**当前 step 累积到该观测点的行数**，不是全历史。

### 6.4 peer 的 `pre_bcast > 0` 是正常的

见 §4 实验 1 的表。peer rank 不执行 join，`pre_bcast` 只是它的"释放前基线"。

### 6.5 MemFabric 之下有些探针不会产出

* 设备视图比较需要"Host 视图是 NPU 可寻址张量"。MemFabric 的 Host 视图是 CPU/GVA 内存 ⇒ 该路径自动切换到 host-view 回调（`mismatches=`）。
* MemFabric 图捕获路径的 `post_write` 也只在 Mooncake 语义下才有意义（`_probe_host_kv_visibility` 在 MemFabric 下会直接返回）。

### 6.6 探针覆盖不到的东西

* 长序列的**键集/地址错误**、PD 传输、容量/块映射：本手册不覆盖（另案）。
* "单 key 错误被 softmax 稀释"这类**概率性表现**：探针只能告诉你"脏了多少行"，不能告诉你"是否会被观察成乱码"。因此**探针非零 ≠ 一定出问题**，需要与业务指标（同一 step 的 token 是否异常）联合判定。

### 6.7 观测扰动

开探针会引入额外 D2H 与算子，可能改变时序。**对照必须同开关**；如果要回答"不开探针时是否也有问题"，请另做一轮纯业务对照。
